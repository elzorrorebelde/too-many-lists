Aprendiendo Rust con Demasiadas Listas Enlazadas

Iter

Muy bien, intentemos implementar Iter. Esta vez no podremos depender de que List nos dé todas las características que queremos. Tendremos que crear el nuestro propio. La lógica básica que queremos es mantener un puntero al nodo actual que queremos producir el siguiente. Como ese nodo puede no existir (la lista está vacía o hemos terminado de iterar), queremos que esa referencia sea un Option. Cuando producimos un elemento, queremos avanzar al nodo next del nodo actual.

Muy bien, intentemos eso:

pub struct Iter<T> {
    next: Option<&Node<T>>,
}

impl<T> List<T> {
    pub fn iter(&self) -> Iter<T> {
        Iter { next: self.head.map(|node| &node) }
    }
}

impl<T> Iterator for Iter<T> {
    type Item = &T;

    fn next(&mut self) -> Option<Self::Item> {
        self.next.map(|node| {
            self.next = node.next.map(|node| &node);
            &node.elem
        })
    }
}

Quizás deberíamos averiguar qué demonios significa esto de los tiempos de vida 'a.

Los tiempos de vida (lifetimes) pueden asustar a mucha gente porque son un cambio a algo que hemos conocido y amado desde el amanecer de la programación. En realidad hemos logrado esquivar los tiempos de vida hasta ahora, aunque han estado enredados a lo largo de nuestros programas todo este tiempo.

Los tiempos de vida son innecesarios en lenguajes con recolector de basura porque el recolector de basura se asegura de que todo viva mágicamente tanto como sea necesario. La mayoría de los datos en Rust se gestionan manualmente, por lo que esos datos necesitan otra solución. C y C++ nos dan un claro ejemplo de lo que pasa si simplemente dejas que la gente tome punteros a datos aleatorios en la pila: una inseguridad generalizada e inmanejable. Esto se puede dividir aproximadamente en dos clases de error:

  • Tener un puntero a algo que salió del ámbito (scope)
  • Tener un puntero a algo que fue mutado

Los tiempos de vida resuelven ambos problemas, y el 99% del tiempo, lo hacen de una manera totalmente transparente.

Entonces, ¿qué es un tiempo de vida?

Muy simplemente, un tiempo de vida es el nombre de una región (~bloque/ámbito) de código en algún lugar de un programa. Eso es todo. Cuando una referencia está etiquetada con un tiempo de vida, estamos diciendo que tiene que ser válida para esa región completa. Diferentes cosas ponen diferentes requisitos sobre cuánto tiempo una referencia debe y puede ser válida. Todo el sistema de tiempos de vida es a su vez solo un sistema de resolución de restricciones que intenta minimizar la región de cada referencia. Si encuentra con éxito un conjunto de tiempos de vida que satisface todas las restricciones, ¡tu programa compila! Si no, obtienes un error diciendo que algo no vivió lo suficiente.

Dentro del cuerpo de una función generalmente no puedes hablar de tiempos de vida, y tampoco querrías hacerlo de todas formas. El compilador tiene información completa y puede inferir todas las restricciones para encontrar los tiempos de vida mínimos. Sin embargo, a nivel de tipo y API, el compilador no tiene toda la información. Requiere que le digas sobre la relación entre diferentes tiempos de vida para que pueda averiguar qué estás haciendo.

En principio, esos tiempos de vida también podrían omitirse, pero entonces verificar todos los préstamos sería un enorme análisis de programa completo que produciría errores alucinantemente no locales. El sistema de Rust significa que toda la verificación de préstamos se puede hacer en cada cuerpo de función de forma independiente, y todos tus errores deberían ser bastante locales (o tus tipos tienen firmas incorrectas).

¡Pero hemos escrito referencias en firmas de funciones antes, y estaba bien! Eso es porque hay ciertos casos que son tan comunes que Rust elegirá automáticamente los tiempos de vida por ti. Esto se llama elisión de tiempos de vida (lifetime elision).

En particular:

// Solo una referencia en la entrada, así que la salida debe derivarse de esa entrada
fn foo(&A) -> &B; // sugar for:
fn foo<'a>(&'a A) -> &'a B;

// Muchas entradas, asumimos que son todas independientes
fn foo(&A, &B, &C); // sugar for:
fn foo<'a, 'b, 'c>(&'a A, &'b B, &'c C);

// Métodos, asumimos que todos los tiempos de vida de salida se derivan de `self`
fn foo(&self, &B, &C) -> &D; // sugar for:
fn foo<'a, 'b, 'c>(&'a self, &'b B, &'c C) -> &'a D;

Entonces, ¿qué significa fn foo<'a>(&'a A) -> &'a B en la práctica? Todo lo que significa es que la entrada debe vivir al menos tanto como la salida. Así que si mantienes la salida durante mucho tiempo, esto expandirá la región que la entrada debe ser válida. Una vez que dejas de usar la salida, el compilador sabrá que está bien que la entrada también se vuelva inválida.

Con este sistema, Rust puede asegurar que nada se usa después de liberarse, y que nada se muta mientras existen referencias pendientes. ¡Solo se asegura de que todas las restricciones funcionen!

🎉 🎉 🎉

Las funciones as_deref y as_deref_mut son estables desde Rust 1.40. Antes de eso necesitarías hacer map(|node| &**node) y map(|node| &mut**node). Puede que estés pensando "vaya, eso de &** es muy chapucero", y no estás equivocado, pero como un buen vino, Rust mejora con el tiempo y ya no necesitamos hacer tal cosa. Normalmente Rust es muy bueno haciendo este tipo de conversión implícitamente, a través de un proceso llamado deref coercion, donde básicamente puede insertar * a través de tu código para que verifique tipos. ¡Puede hacerlo porque tenemos el verificador de préstamos (borrow checker) para asegurarnos de que nunca estropeemos los punteros!

Pero en este caso la clausura en conjunción con el hecho de que tenemos un Option<&T> en lugar de &T es un poco demasiado complicado para que funcione, así que necesitamos ayudarlo siendo explícitos. Afortunadamente esto es bastante raro, en mi experiencia.

Solo por completitud, podríamos darle una pista diferente con el turbofish:

    self.next = node.next.as_ref().map::<&Node<T>, _>(|node| &node);

Verás, map es una función genérica:

pub fn map<U, F>(self, f: F) -> Option<U>
where
  F: FnOnce(T) -> U

El turbofish, ::<>, nos permite decirle al compilador qué creemos que deberían ser los tipos de esos genéricos. En este caso ::<&Node<T>, _> dice "debería devolver un &Node<T>, y no sé/no me importa ese otro tipo".

Esto a su vez permite al compilador saber que &node debería tener aplicada la coerción de desreferencia (deref coercion), ¡así que no necesitamos aplicar manualmente todos esos *!

Pero en este caso no creo que sea realmente una mejora, esto fue solo una excusa mal disimulada para mostrar la coerción de desreferencia y el a veces útil turbofish. 😅

Escribamos una prueba para asegurarnos de que no lo hicimos sin efecto o algo:

#[test]
fn iter() {
    let mut list = List::new();
    list.push(1); list.push(2); list.push(3);

    let mut iter = list.iter();
    assert_eq!(iter.next(), Some(&3));
    assert_eq!(iter.next(), Some(&2));
    assert_eq!(iter.next(), Some(&1));
    assert_eq!(iter.next(), None);

    let mut iter = list.iter();
    assert_eq!(iter.next(), Some(&3));
    assert_eq!(iter.next(), Some(&2));
    assert_eq!(iter.next(), Some(&1));
}

También podemos notar que, a diferencia de into_iter, iter nos permite iterar múltiples veces sobre la misma lista. Esta es la ventaja de usar &self en lugar de self en la definición de la función, la función iter no requirió que moviéramos la lista.
